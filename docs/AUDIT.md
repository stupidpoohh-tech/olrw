# OLRW 이관 전 진단 — 현황 · 개선 지점

> 작성 시점: 이관 착수 전. 코드는 아직 한 줄도 쓰지 않았다.
> 대상: `docs/reference/` (구현 원본), `docs/PORTING-SPEC.md` (설계 정본),
> `neon/migrations/0001_init.sql` (스키마 초안), `docs/reference/DEPLOY.md` (구 Firestore 규칙).
> 기준 질문: **"만나서 하고 싶은 말을 차곡차곡 담고, 만나서 맺고, 아카이브한다"** — 지금 구조가 이걸 하고 있나?

---

## 0. 세 줄 요약

1. **지금 서비스는 데이터가 열려 있다.** 구 Firestore 규칙은 로그인만 하면 남의 전보함에 스스로를 멤버로 넣고 전보 전문을 읽을 수 있다. 이관과 별개로 오늘 막아야 한다.
2. **골격이 목적의 3분의 2만 담고 있다.** "담고"와 "아카이브"는 있는데, **"만나서 맺는다"의 '만남'이 데이터 모델에도 화면에도 없다.** 마감은 만남의 기록이 아니라 그냥 버튼이다.
3. **수신함이 제품의 전제를 스스로 깬다.** 아껴둔 말을 만나기 전에 다 읽어버리면 만나서 할 말이 남지 않는다. 여기가 가장 큰 골격 수정 후보다.

## 1. 현황 파악

### 1-1. 지금 있는 것

| 축 | 상태 |
|---|---|
| 실행 구조 | 단일 `index.html` + 브라우저 Babel 트랜스파일 + React UMD CDN. 빌드 없음 |
| 백엔드 | Firebase compat SDK (Auth + Firestore), config는 HTML에 인라인 |
| 상태 계층 | `store.jsx` 821줄에 `makeLocalStore`(localStorage)와 `makeFirebaseStore` **두 구현이 병렬** |
| 스타일 | `styles.css` 2093줄, 전역 클래스. media query **0개**, `prefers-reduced-motion` **0개** |
| 화면 | 인증 → 온보딩 → (타전실 · 수신함 · 서가) + 만남 마감 4단계 모달 |
| 자산 | 타자기 사진 836KB PNG 1장, 오디오 0바이트(Web Audio 합성) |

### 1-2. 데이터 흐름 (현재)

```
boxes(전보함) ── members{uid:{name,paper,type}} · currentVol · coupleCode
   ├── telegrams[]   { from, text, time, vol }         ← 현재 권에 쌓임
   └── volumes[]     { vol, title, cover, period, count, telegrams[스냅샷] }
```

마감(`closeVol`)이 하는 일: 현재 vol의 전보를 모아 → 발신인 이름·용지색을 **그 시점 값으로 복사** → `volumes`에 스냅샷 저장 → 원본 전보 **삭제** → `currentVol + 1`.

스냅샷 설계는 옳다(이름·색을 나중에 바꿔도 과거 책이 안 변한다). **유지할 것.**

### 1-3. 이미 잘 잡혀 있어 건드리지 말 것

- 색의 역할 분리: 용지색=발신인(공개) / 타자기색=전보함(개인). 정보로서의 색.
- 제본 애니메이션 타임라인 5.8초, 종이 12장 `--final` ±2.5도. 완벽 정렬을 피한 판단이 좋다.
- Web Audio 합성 사운드. 에셋 0바이트.
- 반경 최대 6px, 액센트 `#8a3a31` 하나. 절제가 제품의 인상을 만든다.
- 정원 4명 상한. 컨셉 보호를 위한 의도적 제약 — 올리지 않는다.
- 카피 톤(담백한 존댓말, 이모지 없음).

## 2. 긴급 — 이관과 별개로 오늘 처리할 것

`docs/reference/DEPLOY.md`의 현행 Firestore 규칙:

```js
match /rooms/{roomId} {
  allow read:   if signedIn();                                   // ①
  allow update: if signedIn()
                 && (request.auth.uid in resource.data.memberUids
                  || request.auth.uid in request.resource.data.memberUids);  // ②
  match /telegrams/{tgId} { allow read, write: if roomMember(); }
}
match /codes/{code} { allow read: if signedIn(); }                 // ③
```

- **① 로그인한 아무나 모든 전보함 문서를 읽는다** — 이름, 초대 코드, 멤버 구성 전부.
- **② 로그인한 아무나 자기 uid를 `memberUids`에 넣어 업데이트할 수 있다.** 규칙이 "새 멤버의 참여"를 허용하려고 `request.resource.data`(=쓰기 후 상태)를 검사하는데, 이건 **초대 코드 없이 아무 방에나 들어가는 문**이다. 들어가면 `roomMember()`가 통과하므로 그 방의 전보 전문을 읽고 쓰고 지울 수 있다.
- **③ 초대 코드 컬렉션 전체 열람 가능** — 코드를 훑어 방을 찾을 수 있다.
- Firebase config가 `index.html`에 인라인이고 가입이 열려 있다. 웹 API 키 자체는 공개 전제가 맞지만, **위 규칙과 결합하면 "가입만 하면 전부 열람"이 된다.**

→ **조치:** 이관 완료를 기다리지 말고 지금 Firestore 규칙을 잠근다(최소한 `rooms` read를 `amMember()`로, update에서 `request.resource.data` 기반 참여 경로 제거). 참여는 어차피 새 구조에서 RPC로 옮긴다. 기존 데이터가 본인 테스트용뿐이면 그냥 규칙을 전부 `false`로 닫고 이관하는 편이 빠르다.

## 3. 목적 대비 골격 갭 (제품)

목적: **담는다 → 만나서 맺는다 → 아카이브한다.** 지금 구조를 이 세 마디에 대보면.

### G1. '만남'이 어디에도 없다 — 가장 큰 구멍

제품의 중심 사건은 만남인데, 데이터 모델에 `meeting`이 없다. 있는 것은 `volumes.closed_at`뿐이고, 권의 기간(`period`)조차 **전보 타임스탬프의 최소·최대에서 역산**한다. 즉 앱은 "우리가 언제 만나기로 했는지", "지난 만남이 언제였는지"를 모른다.

그 결과 이 제품이 가장 잘할 수 있는 질문에 답을 못 한다:
> **"다음 만남까지 12일, 지금 7통이 쌓였습니다."**

이 한 줄이 없으면 타전실은 그냥 메모장이다. 쌓이는 것에 방향이 생기려면 도착점이 있어야 한다.

**제안:** `meetings`를 1급 개념으로 올린다. **VOL = 만남과 만남 사이.**
- 전보함에 `next_meeting_at`(선택, 미정 가능)을 둔다.
- 타전실 상단에 D-카운트와 이번 권 누적 수.
- 마감하면 그 만남이 `volumes.met_at`으로 기록되고, 다음 만남 날짜를 잡는 화면으로 자연스럽게 이어진다.
- 날짜는 **선택 사항**이어야 한다. "언젠가 만나면"도 이 제품의 정당한 사용법이다. 미정이면 D-카운트 자리에 누적 수만 보인다.

### G2. 수신함이 제품의 전제를 깬다 — 두 번째로 큰 구멍

`InboxView`는 이번 권에서 **남이 보낸 전보를 즉시 전문 공개**한다. "만나서 하려던 말"을 만나기 전에 다 읽으면, 만나서 할 말이 남지 않는다. 스펙의 원칙 1("느림이 기능이다")은 읽음 표시를 금지하는 데서 멈췄지만, 진짜 문제는 그 아래에 있다.

**제안: 봉인(封) 모드.** 남의 전보는 만나기 전까지 **봉투**로만 보인다.
- 보이는 것: 발신인 용지색 + 도착 시각 + 분량(짧음/보통/긺) — 존재감은 있고 내용은 없다.
- 봉인이 풀리는 시점: **만남 마감의 '함께 읽기' 단계**(G3).
- **전보함 단위 설정**으로 둔다: `봉인함` / `열린함`. 기본값은 봉인함. 이 제품이 무엇인지 첫 화면에서 설명하는 장치이기도 하다.
- 봉인함에서도 **내 전보는 언제나 보인다**(타전실의 '최근 송신'). 자기가 뭘 보냈는지도 모르면 곤란하다.

이건 기능 추가가 아니라 **원래 컨셉의 완성**이다. 지금은 컨셉이 UI에서 한 번 무너져 있다.

### G3. '만나서 맺는' 순간이 앱에 없다

현재 만남 마감: `confirm → customize → binding(5.8s) → done`. 확인하고, 표지 고르고, 애니메이션 보고, 끝. **만나서 그 말들을 실제로 나누는 순간이 통째로 빠져 있다.** 제본은 그 순간의 *결과*인데, 결과만 있고 사건이 없다.

**제안: `confirm`과 `customize` 사이에 `함께 읽기(낭독)` 단계를 넣는다.**
- 이번 권의 전보를 **한 장씩** 넘긴다. 한 화면에 한 통. 발신인 용지색 그대로.
- 봉인된 전보가 여기서 처음 열린다 — 봉인의 회수 지점.
- 넘길 때 `playReturn()`(캐리지 슬라이드). 이미 있는 사운드다.
- 마지막 장에서 "다 읽었습니다 → 제본으로".
- 건너뛰기 가능해야 한다(카페에서 4명이 30통을 다 넘기진 않는다). 단, 건너뛰면 봉인은 그대로 풀되 "읽지 않고 제본했습니다"를 권 표지 안쪽에 남긴다.

이 단계가 들어가면 제본 애니메이션이 비로소 **의식의 마침표**가 된다. 지금은 그냥 로딩 화면이다.

### G4. 마감이 단독 행위다

`closeVol`을 누구나 혼자 누른다. 다른 사람이 아직 못 읽은 전보가 그대로 책으로 넘어간다. 스펙 §8도 미결로 남겼다.

**제안: 마감은 제안 + 동의.**
- 누구든 "만남 마감"을 **발의**한다 → 다른 멤버에게 대기 상태로 보인다 → **과반(2인 방은 전원)이 동의**하면 진행.
- 예외: **같은 자리에 있을 때**가 정상 상황이므로, 발의 후 15분 이내 동의는 그냥 서로 폰을 보며 누르면 된다. 무겁지 않다.
- 방장 단독 마감은 **탈출구로만** 남긴다(멤버가 응답 없이 오래 방치될 때).

"방장 전용"보다 "동의"가 맞다. 이 제품에 위계는 어울리지 않는다.

### G5. 파괴적 동작이 너무 가볍다

원칙 4는 "소유물처럼 다룬다"인데 실제 UI는:
- 모든 전보 카드에 `×` 버튼 + `window.confirm` 한 번 → 즉시 하드 삭제.
- 서가의 권도 confirm 한 번 → **"되돌릴 수 없습니다"라고 써 놓고 진짜로 지운다.**
- 스펙은 soft delete를 요구하는데 스키마의 `deleted_at`은 **아무 데서도 읽거나 쓰지 않는다.**

**제안:**
- 전보: 발신 후 **3분 안에만 '회수'** 가능. 그 뒤엔 못 지운다. 이미 타전된 것이다.
- 권: 삭제 대신 **'서가에서 내리기'**(보관 해제) + 30일 유예 후 파기. 하드 삭제 경로는 UI에서 없앤다.
- 카드의 `×`는 없앤다. 회수는 카드를 길게 눌러 나오는 메뉴로.

### G6. 서가가 다시 열릴 이유가 없다 (선택)

책은 꽂히지만 다시 꺼낼 계기가 없다. 이 제품이 알림을 넣는다면 푸시가 아니라 이쪽이다 — 스펙 §8도 "주간 요약 같은 느린 알림"이라고 적어 두었다.
- **"작년 오늘, VOL.3에 이 전보가 있었습니다."** 월 1회 정도.
- 권 단위 **내보내기**(PDF / 인쇄용 조판). 실물 제본은 이 제품의 자연스러운 종착점이다.

우선순위는 낮다. 1:1 포팅 + G1~G4 이후.

### G7. 실시간 구독은 옮기지 않는 편이 낫다

현재 `makeFirebaseStore`는 `onSnapshot`으로 전보를 실시간 스트리밍한다. 그런데 원칙 1은 "실시간 대화 UI 금지"다. **구조가 원칙과 반대로 서 있다.** 봉인 모드(G2)를 넣으면 실시간이 전할 정보 자체가 거의 없다.

**제안:** Supabase Realtime을 켜지 않는다. 화면 진입 시 fetch + 당겨서 새로고침. 코드도 줄고 원칙도 지켜진다.

## 4. 이관 자료 자체의 결함 (지금 고쳐서 시작할 것)

### 4-1. 스키마 · RLS (`0001_init.sql`)

| # | 문제 | 영향 |
|---|---|---|
| S1 | `invite_code` 체크가 `^[A-Z0-9]{6}$`인데 앱은 `ABCD-2345`(8자 + 하이픈)를 만든다 | **어떤 전보함도 생성되지 않는다.** 스펙과 구현의 정면 충돌 |
| S2 | `members_insert with check (user_id = auth.uid())` | **box_id만 알면 아무 방에나 자기를 넣을 수 있다.** 구 Firestore 규칙 ②와 같은 구멍이 그대로 재현됨. 정원 트리거는 4명 이하면 통과시킨다 |
| S3 | `vol_insert` / `page_insert`가 `is_member`면 통과 | 멤버가 **위조된 과거 책과 페이지를 직접 써넣을 수 있다.** 제본은 서버가 해야 한다 |
| S4 | `boxes_insert` 후 `boxes_read`는 `is_member(id)` | 방을 만든 직후 **자기 방을 못 읽는다.** `INSERT ... RETURNING`은 SELECT 정책을 요구하므로 생성 자체가 실패한다 |
| S5 | `boxes_update` / `profiles_update` / `tg_update`에 `with check`가 없다 | 소유자가 `owner_id`·`invite_code`를 바꾸거나, 작성자가 전보의 `box_id`·`vol`을 다른 방으로 옮길 수 있다 |
| S6 | `body` 길이 체크 1~2000 | 앱의 `CHAR_LIMIT`는 **100**이다. DB가 훨씬 느슨하다 |
| S7 | `cover` 한 컬럼에 색 id와 `'photo'`가 섞이고 `cover_url`이 따로 | 유니온을 컬럼 하나로 흉내 냄. `cover_kind` + `cover_value`로 분리 |
| S8 | `owner_id references profiles on delete restrict`, 소유자 이양 로직 없음 | 방장이 탈퇴하면 방이 잠긴다. 참조 구현에는 `ownerUid = remaining[0]` 이양이 있는데 SQL에는 없다 |
| S9 | `deleted_at` 컬럼이 있으나 어떤 정책·쿼리도 쓰지 않는다 | soft delete가 이름만 있다 |
| S10 | `join_box` RPC에 정원 초과 구분 메시지·코드 시도 제한이 없다 | 코드 브루트포스가 열려 있다 (32^8이라 당장 위험하진 않지만 rate limit은 필요) |
| S11 | Storage(`covers`) 정책이 마이그레이션에 없다 | 문서에만 있고 코드로 남지 않는다 |
| **S12** | **구현 중 발견.** SELECT 정책에 `deleted_at is null`을 넣으면 소프트 삭제가 아예 불가능하다 | UPDATE는 갱신된 행이 SELECT 정책에도 맞아야 통과한다. 회수가 행을 스스로 안 보이게 만들어 **자기 전보조차 지울 수 없었다.** 작성자에게는 자기가 회수한 행을 열어 두고, 읽기 경로인 `telegram_envelopes` 뷰가 걸러낸다 |

**정리:** 쓰기 경로 중 **박스 생성 · 참여 · 제본**은 RLS로 풀 문제가 아니라 **`security definer` RPC 3개**로 닫아야 한다. 테이블 직접 INSERT는 `telegrams`만 남긴다.

### 4-2. 마감 트랜잭션

`closeVol`이 전부 클라이언트에서 돈다: 전보 조회 → 스냅샷 조립 → 권 생성 → 원본 삭제 → `currentVol + 1`. 두 명이 동시에 누르면 **같은 vol 번호로 두 권이 생기거나 전보가 사라진다.** Firestore batch도 조건부 쓰기가 아니라서 막지 못한다.

→ `close_volume(box_id, title, cover_kind, cover_value)` RPC 하나로 옮기고, `boxes.current_vol`을 조건부로 증가시켜 경합을 막는다. 스냅샷도 서버가 만든다(위조 불가).

### 4-3. 참조 구현의 실제 버그 (같은 실수를 옮기지 않도록)

- **`ritual.jsx` — 비동기 무시:** `handleBindingDone`이 `onConfirmClose(...)`의 반환값을 동기로 쓴다. Firebase 스토어에서는 **Promise가 반환**되므로 `closedVol.vol`이 `undefined` → 완료 화면이 **"VOL.undefined"**.
- **`ritual.jsx` — 0건 무음 실패:** 전보가 0건이면 `closeVol`이 `null`을 반환하는데, `phase`는 이미 `'done'`이고 `closedVol && ...` 조건에 걸려 **아무것도 안 그린다.** 5.8초 애니메이션 끝에 빈 화면. (`meet-btn`이 `disabled`라 잘 안 걸리지만, 마지막 전보를 지우고 마감하면 재현된다.)
- **`app.jsx` — 낙관적 UI 없음:** `sendTelegram`이 실패해도 사용자에게 아무 표시가 없다. `catch`가 없다.
- **`transmit.jsx` — 한글 IME:** 숨긴 `<textarea>` + 별도 `typed-display` 구조에서 `onChange`만으로 글자 수와 타건음을 처리한다. 조합 중인 한글(`ㅎ→하→한`)이 매 단계 `onChange`를 발생시켜 **글자 수가 튀고 타건음이 과하게 울린다.** `compositionstart`/`compositionend`로 감싸야 한다.
- **`store.jsx` — 비밀번호 해시:** 로컬 스토어의 `hashPw`가 djb2다. 데모용이므로 이관하면 사라지지만, `MemoryStore`로 옮길 때 **가져가지 말 것**.
- **`archive.jsx` — 표지 판별:** `cover.startsWith('data:')`로 이미지 여부를 문자열 검사한다. S7의 컬럼 분리로 없앤다.

### 4-4. 프런트엔드 · 접근성

- **media query 0개.** `max-width: 460px` 고정 컬럼. 데스크톱에서 좁은 띠 하나로 보인다. 모바일 우선은 맞지만 최소한 태블릿/데스크톱 여백 처리는 필요하다.
- **`user-scalable=no, maximum-scale=1.0`** — 핀치 줌 차단. 접근성 위반이고 iOS 최신 사파리는 무시한다. 지운다.
- **`prefers-reduced-motion` 0개.** 5.8초 애니메이션에 스킵 경로가 없다. 스펙도 누락으로 인정한 부분 — 0.4초 페이드 경로를 넣는다.
- **용지색이 유일한 발신인 단서.** 색약 사용자는 8색 파스텔을 구분하지 못한다. 스펙 §4-1도 지적. **테두리 스타일(실선/파선/이중선/점선)** 을 색과 짝지어 비색상 단서를 만든다. 색 8종 × 테두리 4종이면 4인 방에서 충돌이 없다.
- **폰트 CDN `@import` 2개** (jsdelivr + Google Fonts). 렌더 블로킹 + 외부 의존. self-host로 옮긴다.
- **타자기 사진 836KB PNG.** WebP/AVIF로 바꾸면 1/5 수준. 필터를 거는 이미지라 화질 손실도 잘 안 보인다.
- **폰트 불일치:** 스펙은 장식체를 `Fraunces`로 못박았는데 `ritual.jsx`가 인라인 스타일에서 `'Noto Serif KR'`과 `'Cormorant Garamond'`를 쓴다. 로드되지도 않는 폰트라 조용히 폴백 중이다. → Fraunces로 통일.

### 4-5. §4-2 타자기색이 실제로는 작동하지 않는다 (단계 2에서 발견) — **결정 필요**

전보함을 색으로 구분한다는 §4-2 의 장치가 **번들에 담겨 온 사진으로는 동작하지 않는다.**
참조 구현도 같은 파일(`assets/typewriter.png`)을 썼으므로, 기존 서비스에서도 줄곧 이랬을 것이다.

**원인.** §4-2 는 원본 사진이 *채도 높은 청록색*이라고 전제하고 "채도를 먼저 낮추고 hue-rotate"
한다. 그런데 실제 파일은 **평균 채도 0.084** 로 이미 거의 무채색이다(본체 대표색 `rgb(160,176,160)`).
낮출 채도가 없고, 무채색에 건 `hue-rotate` 는 아무 일도 하지 않는다.

**측정.** 본체 픽셀 67,659개의 평균색을 여덟 필터에 대해 잰 결과:

| | 결과 평균색 | 채도 |
|---|---|---|
| green | `rgb(154,158,153)` | 0.032 |
| teal | `rgb(151,156,152)` | 0.032 |
| blue | `rgb(150,155,154)` | 0.032 |
| plum | `rgb(152,155,156)` | 0.026 |
| rose | `rgb(157,156,161)` | 0.031 |
| terra | `rgb(161,157,162)` | 0.031 |
| ochre | `rgb(165,160,164)` | 0.030 |
| stone | `rgb(156,157,156)` | 0.006 |

가장 가까운 두 색(green↔teal)의 거리가 **ΔE 1.0**, 가장 먼 쌍도 6.4다.
ΔE 1 은 나란히 놓고도 거의 구분되지 않는 거리다. `pnpm tint:check` 로 재현한다.

**선택지.**

| | 방법 | 결과 | 대가 |
|---|---|---|---|
| **가** | 채도가 살아있는 **원본 사진**을 받아 교체 | §4-2 값이 손대지 않고 그대로 작동한다 | 원본 파일이 있어야 한다 |
| **나** | `grayscale(1) sepia(1) hue-rotate() saturate()` 기반으로 **filter 값만 다시 계산** | 여덟 색 모두 목표 tint 에 **ΔE ≤ 0.7** 로 맞고, 색 간 거리 **ΔE 11.6** 로 벌어진다 | 사진의 **흰 배경까지 물든다.** 배경이 불투명하게 구워져 있어(알파 0) 본체만 골라낼 수 없다. 배경을 지워 투명 PNG/WebP 로 만들면 해결되고, 836KB 도 같이 줄어든다 |
| **다** | **SVG 일러스트**로 교체 | 색 제어가 정확하고 파일이 가볍다 | 사진의 질감이 제품 인상에 기여한다고 §4-2 가 경고했다 |

**추천: 가 → 나.** 원본 사진이 있으면 그게 가장 정직하다. 없으면 **나**로 가되 배경을 지운다.
`tint`(대표색 8종)는 어느 쪽이든 그대로 둔다 — 바뀌는 것은 그 색에 도달하는 방법뿐이다.

지금 코드에는 **§4-2 값을 그대로 두었다.** 디자인 값을 임의로 바꾸지 않는다(CLAUDE.md 절대 규칙 7).
결정이 나면 그때 반영한다.

## 5. 제안하는 새 골격

기존 스펙의 스택(Vite + React + TS + Supabase + Vercel)은 그대로 간다. 바꾸는 것은 **개념 모델**이다.

```
box (전보함)
 ├─ members (≤4)           paper_color(공개) · type_color(개인) · 봉인모드 설정
 ├─ meetings ★신규          scheduled_at(선택) · met_at · status
 │     └─ 만남 하나가 권 하나를 닫는다.  VOL = 만남과 만남 사이
 ├─ telegrams               body · vol · sealed_until ★  · retracted_at ★
 └─ volumes                 met_at ★ · title · cover_kind/value · pages[스냅샷]
```

**화면 흐름**

```
타전실(홈)   다음 만남까지 D-12 · 이번 권 7통          ← G1
             [타자기 + 내 용지] 쓰기
             내가 보낸 것 (전문)
수신함       봉투 7개 (발신인 색 · 시각 · 분량)         ← G2
             "만나서 열립니다"
만남 마감    confirm → [함께 읽기 ★] → customize        ← G3
             → binding(5.8s / reduced-motion 시 0.4s 페이드)
             → done → 다음 만남 잡기 ★                  ← G1
서가         제본된 권. 내리기(30일 유예)                ← G5
```

**쓰기 경로 3개만 서버 RPC로**

```
create_box(name, paper, type)          → box_id, invite_code
join_box(code, paper, type)            → box_id, name        (정원·중복·rate limit)
close_volume(box_id, title, cover…)    → volume_id           (스냅샷 · 경합 방지 · 동의 검증)
```
테이블 직접 INSERT는 `telegrams` 하나만. 나머지는 `revoke insert`.

**디자인 값은 그대로.** §3 토큰, §4 색, §6 타임라인·이징·사운드 파라미터는 손대지 않는다. 바꾸는 것은 구조와 흐름뿐이다.

## 6. 로드맵

기존 §9 순서를 유지하되, 골격 변경은 **스키마 단계에서 미리 자리를 만들고** 화면은 나중에 채운다. 나중에 마이그레이션으로 뜯는 것보다 싸다.

| 단계 | 내용 | 골격 변경 |
|---|---|---|
| 1 | 스키마 + RLS + RPC 3종 | `meetings`, `sealed_until`, `retracted_at`, `cover_kind/value` **컬럼까지 지금 만든다** |
| 2 | 디자인 토큰 · 색 시스템 (§3·§4 값 그대로) | 용지 **테두리 스타일** 비색상 단서 추가 |
| 3 | 인증 → 온보딩 → 전보함 전환 바 | 온보딩에 **봉인함/열린함** 선택 |
| 4 | 타전실 → 수신함 → 서가 | 타전실 **D-카운트**, 수신함 **봉투 UI** |
| 5 | 만남 마감 + 제본 애니메이션 (타임라인 그대로) | **함께 읽기** 단계, **동의 절차**, reduced-motion 경로 |
| 6 | 사운드 (§6-1 파라미터 그대로) | 함께 읽기 넘김에 `playReturn` 재사용 |
| 7 | 다음 만남 잡기 · 권 내리기 유예 · (선택) 느린 알림 · 내보내기 | |

**단계 1은 결정이 끝나야 시작할 수 있다.** 그 아래는 순서대로 진행 가능.
