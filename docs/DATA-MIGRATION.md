### 옮기는 것 (사용자 결정)

```
전보함 2 · 이번 권 전보 1 · 제본된 권 10 · 제본된 전보 109 · 참여자 3
  견본 전보함 1   3권 34통   (안 · 보 · 에피)
  견본 전보함 2     7권 75통   (안 · 에피)
```

**옮기지 않는 둘.** 지우는 것이 아니라 `legacy-export.json` 에 그대로 남아 있다.

```
  견본 전보함 3     2권  4통   (안 · 라)
  견본 전보함 4     2권  4통   (안 혼자)
```

마음이 바뀌면 `neon/migration/build.mjs` 의 `BOXES` 에 roomId 한 줄을 더하고
스크립트를 다시 돌리면 된다. 필요한 사람 목록도 따라서 늘어난다 — SQL 은
**고른 전보함에 실제로 등장하는 사람만** uuid 를 받는다. 그래서 지금은 라이
빠져 있고, 가입해야 하는 사람이 넷이 아니라 셋이다.

`legacy-export.json` 은 원본 그대로다. 딱 하나 바꾼 것: 표지 사진의
base64(`data:image/jpeg;…`)를 `"photo"` 로 줄였다. Neon 에는 Storage 가 없어
어차피 색 표지만 쓴다 (D14). 사진 표지가 필요해지면 그때 다시 꺼낸다 —
`migrate.html` 을 지우기 전이라면 언제든.

### 심는 SQL

```
neon/migration/
  legacy-export.json   원본 (손대지 않는다)
  build.mjs            원본 → SQL 을 뽑는 스크립트. 판단이 담긴 곳은 여기다
  0002_legacy.sql      뽑아낸 결과. 손으로 고치지 않는다 (§1 의 uuid 네 줄만 예외)
  dryrun.sh            일회용 Postgres 에 그대로 부어 보는 예행연습
```

`0002_legacy.sql` 은 테이블에 직접 INSERT 한다. 이관은 소유자·초대코드·`created_at`
을 원본 그대로 살려야 해서 `create_box` / `join_box` 로는 할 수 없다. **앱 코드에는
그 문을 열지 않는다** — 마이그레이션 파일 안에서만이다.

모든 id 를 옛 id 에서 결정론적으로 뽑고(같은 원본 → 같은 uuid), INSERT 는 전부
`on conflict do nothing` 이다. 두 번 부어도 행이 늘지 않는다 — 예행연습에서 확인했다.

## 남은 일 — 순서대로

네 단계다. **1번은 각자, 2·3·4번은 안 혼자** 한다.

### 다 모이기를 기다리지 않아도 된다

아는 사람의 uuid 만 채워 부으면, **그 사람들만으로 온전한 전보함**이 먼저 들어간다.
나머지는 조용히 건너뛰고, 빠진 사람이 나중에 들어온 뒤 **같은 파일을 그대로 다시**
부으면 그때 들어간다. 모든 id 를 옛 id 에서 결정론적으로 뽑으므로 이미 들어간 것은
두 번 들어가지 않는다.

| 지금 아는 사람 | 이번에 들어가는 것 | 남는 것 |
|---|---|---|
| 안 · 에피 | **견본 전보함 2** 7권 75통 | 견본 전보함 1 |
| 안 · 보 · 에피 | 둘 다 | — |

반쪽으로는 들어가지 않는다. 한 사람이라도 없으면 그 전보함은 **통째로** 건너뛴다 —
보의 전보만 빠진 채 `견본 전보함 1` 가 들어가면 권마다 쪽수가 어긋나 서가가
거짓말을 한다.

### 1. 각자 새 앱에서 가입한다

옛 파이어베이스 uid 와 새 Neon 계정 uuid 는 서로 남이다. 이어 붙이려면 계정이
먼저 있어야 한다.

**주소**: https://olrw-8pt.pages.dev

| 누가 | 무엇을 |
|---|---|
| 안 | 가입 |
| 보 | 가입 |
| 에피 | 가입 |

**가입만으로는 부족하고, 한 번 들어와 있어야 합니다.** 계정은 로그인 서버가
들고 있고, 우리가 짝지을 `profiles` 행은 **앱 화면이 뜬 순간** 만들어집니다.
로그인이 막혀 아직 못 들어온 사람은 uuid 를 받을 수 없습니다.

**세 가지만 지켜 주면 됩니다.**

1. 아래쪽 **계정 만들기** 를 누릅니다. 화면 위쪽 "체험 모드" 는 저장되지 않습니다.
2. **표시 이름을 옛 앱과 똑같이** 적습니다 — `안` · `보` · `에피`.
   다르게 적어도 옛 책 속 이름은 안 바뀌지만(제본은 스냅샷이다), 전보함 위쪽
   참여자 줄에는 새 이름이 뜨므로 한 화면에 두 이름이 보입니다.
3. 가입하면 **"전보함 만들기" 화면**이 나옵니다. **거기서 멈춥니다.**
   여기서 만들면 옛 전보함 옆에 빈 전보함이 하나 더 생깁니다.

> **초대 코드는 주고받지 않습니다.** 옛 코드(`ABCD-2345` · `EFGH-6789`)를 그대로
> 살려 옮기고, 참여자도 함께 넣습니다. 3번이 끝나고 새로고침하면 두 전보함이
> **이미 들어가 있는 상태로** 나타납니다.

### 2. uuid 는 이미 채워져 있습니다

세 사람 모두 받아서 `build.mjs` 의 `KNOWN` 에 적어 두었고, `0002_legacy.sql` §1 에
그 값이 들어간 채로 생성됩니다. **§1 을 손댈 일이 없습니다** — 바로 §3 으로 갑니다.

```sql
insert into legacy_user (legacy_uid, label, id) values
  ('AAAAAAAAAAAAAAAAAAAAAAAAAAA1', '안 (you@example.com)', '00000000-0000-4000-8000-000000000001'),
  ('BBBBBBBBBBBBBBBBBBBBBBBBBBB2', '보',                       '00000000-0000-4000-8000-000000000002'),
  ('CCCCCCCCCCCCCCCCCCCCCCCCCCC3', '에피',                         '00000000-0000-4000-8000-000000000003')
;
```

나중에 사람이 바뀌거나 계정을 다시 만들면 **`build.mjs` 의 `KNOWN` 을 고쳐 다시
뽑습니다.** 생성된 SQL 을 손으로 고치면 다음에 다시 뽑을 때 사라집니다.

<details>

**2-1. Neon 콘솔에서 uuid 를 봅니다.**

Neon 콘솔 → 왼쪽 **Postgres database** → **Tables** → 왼쪽 목록에서 `profiles`

`display_name` 으로 사람을 찾고 `id` 칸의 값을 복사합니다. 이렇게 생겼습니다:

```
019c3f7a-2b81-7c4e-9d15-6a2f8e4b0c33
```

**Auth → Users 탭의 `ID` 도 같은 값입니다.** 어느 쪽을 봐도 됩니다. 다만 거기에는
있는데 `profiles` 에 없는 사람이 있을 수 있습니다 — 계정만 만들고 아직 앱 화면까지
못 들어온 경우입니다. 그 사람의 uuid 를 넣으면 SQL 이 §1 에서 멈춰 알려 줍니다.

**안 보이는 사람은 그냥 `null` 로 둡니다.** 그 사람이 필요한 전보함만 이번에
건너뜁니다.

**2-2. `neon/migration/0002_legacy.sql` 을 열어 §1 을 채웁니다.**

파일 위쪽 `═══ 1. 사람 짝짓기 — 여기만 채운다` 아래에 세 줄이 있습니다.
`null` 을 받은 uuid 로 바꿉니다. **작은따옴표를 씌웁니다.**

바꾸기 전:

```sql

  ('CCCCCCCCCCCCCCCCCCCCCCCCCCC3', '에피',                         null)
;
```

```sql
insert into legacy_user (legacy_uid, label, id) values

```

바꾼 뒤 — **보를 아직 모르는 경우**. `null` 을 그대로 둡니다:

```sql
insert into legacy_user (legacy_uid, label, id) values
  ('AAAAAAAAAAAAAAAAAAAAAAAAAAA1', '안 (you@example.com)', '019c3f7a-2b81-7c4e-9d15-6a2f8e4b0c33'),
  ('BBBBBBBBBBBBBBBBBBBBBBBBBBB2', '보',                       null),
```

다시** 부으면 `견본 전보함 1` 가 들어갑니다.

- 왼쪽의 긴 옛 uid 는 **건드리지 않습니다.** 그게 누구인지 가리키는 이름표입니다
- 줄 끝의 쉼표와 마지막 줄의 세미콜론(`;`)은 그대로 둡니다
- **이 파일에서 사람이 손대는 곳은 여기뿐입니다.** 나머지는 스크립트가 만든 것이라
  고치면 다음에 다시 뽑을 때 사라집니다

### 3. Neon 에 붓는다 (안)

Neon 콘솔 → 왼쪽 **Postgres database** → **SQL Editor**

채운 `0002_legacy.sql` **전체를** 붙여넣고 **Run**.

- **파일 전체를 한 번에** 붙여넣습니다. 조각내서 돌리지 않습니다
- 스키마를 건드리지 않으므로 **Refresh schema cache 는 누르지 않아도 됩니다**

**셋 다 채웠으면** 아래쪽 메시지 칸에 이렇게 뜹니다.

```
NOTICE: 견본 전보함 1 : 참여 3/3 · 이번 권 전보 1/1 · 제본된 권 3/3 · 쪽 34/34
NOTICE: 견본 전보함 2 : 참여 2/2 · 이번 권 전보 0/0 · 제본된 권 7/7 · 쪽 75/75
NOTICE: 들어간 전보함 2 · 건너뛴 전보함 0
```

**보를 비워 둔 경우**에는 이렇게 뜹니다. 건너뛴 것은 실패가 아닙니다.

```
NOTICE: 아직 uuid 가 없는 사람: 보
NOTICE: 이번에 건너뛰는 전보함: 견본 전보함 1 (그 사람이 가입한 뒤 이 파일을 다시 부으면 들어갑니다)
NOTICE: 견본 전보함 2 : 참여 2/2 · 이번 권 전보 0/0 · 제본된 권 7/7 · 쪽 75/75
NOTICE: 들어간 전보함 1 · 건너뛴 전보함 1
```

**들어가기로 한 전보함에서 숫자가 하나라도 모자라면 SQL 이 전부 되돌립니다.**
반쯤 들어간 서가로 남지 않으므로, 고쳐서 다시 붙여넣으면 됩니다.
**두 번 돌려도 행이 늘지 않습니다.**

멈췄을 때 나오는 말:

| 메시지 | 뜻 | 할 일 |
|---|---|---|
| `uuid 를 하나도 채우지 않았습니다` | §1 이 전부 `null` 이다 | 2 |
| `invalid input syntax for type uuid` | uuid 에 따옴표를 안 씌웠거나 글자가 빠졌다 | 2-2 |
| `… : 들어간 행이 모자랍니다` | 그 전보함이 반만 들어갔다 (전부 되돌아갔다) | 그대로 다시 Run |
| `쪽수가 어긋난 권이 있습니다` | 권에 적힌 쪽수와 실제 쪽 수가 다르다 (전부 되돌아갔다) | 그대로 다시 Run · 계속되면 알려 주세요 |
| `들어간 전보함이 하나도 없습니다` | 채운 사람만으로 온전한 전보함이 없다 | 2-1 로 돌아가 한 명 더 채웁니다 |

### 프로필은 SQL 이 알아서 세웁니다

`profiles` 행은 원래 앱이 첫 로그인 때 만듭니다. 계정만 만들고 **앱 화면까지 아직
못 들어온 사람**은 그 행이 없고, `boxes.owner_id` 와 `volume_pages.author_id` 가
`profiles` 를 참조하므로 이관이 통째로 막힙니다.

그래서 §1 다음에 없는 프로필을 **옛 이름으로 세웁니다.** 무엇을 세웠는지 알려 줍니다.

```
NOTICE: 프로필을 새로 세운 사람: 보 (00000000-0000-4000-8000-000000000002)
```

그 사람이 나중에 로그인해도 이름이 덮이지 않습니다 — `ensure_profile()` 은
`on conflict (id) do nothing` 입니다. 옛 이름이 그대로 남습니다.

**여기 낯선 이름이나 모르는 uuid 가 있으면 uuid 를 잘못 넣은 것입니다.** 아래
「잘못 넣었을 때」로 되돌리고 다시 부으면 됩니다.

### 잘못 넣었을 때

전부 지우고 처음부터 다시 부을 수 있습니다. 옮긴 것만 지우므로 앱에서 새로 만든
전보함은 건드리지 않습니다.

```sql
begin;
delete from volume_pages where volume_id in (
  select id from volumes where box_id in (
    'd548f9a7-aa87-65a7-362d-99ff8486a2de',   -- 견본 전보함 1
    'f20bd636-9b7a-f0dd-197a-2d3252f3f910')); -- 견본 전보함 2
delete from volumes     where box_id in (
  'd548f9a7-aa87-65a7-362d-99ff8486a2de', 'f20bd636-9b7a-f0dd-197a-2d3252f3f910');
delete from telegrams   where box_id in (
  'd548f9a7-aa87-65a7-362d-99ff8486a2de', 'f20bd636-9b7a-f0dd-197a-2d3252f3f910');
delete from box_members where box_id in (
  'd548f9a7-aa87-65a7-362d-99ff8486a2de', 'f20bd636-9b7a-f0dd-197a-2d3252f3f910');
delete from boxes       where id in (
  'd548f9a7-aa87-65a7-362d-99ff8486a2de', 'f20bd636-9b7a-f0dd-197a-2d3252f3f910');
commit;
```

이관이 잘못 세운 프로필까지 지우려면 그 uuid 로 한 줄 더 돌립니다. 실제로 쓰는
사람의 프로필이면 다른 곳에서 참조하고 있어 삭제가 막히므로, 지워지는 것은
쓰이지 않는 프로필뿐입니다.

```sql
delete from profiles where id = '지울-uuid';
```

### 3-1. 나중에 나머지를 마저 붓는다

건너뛴 전보함이 있었다면, 그 사람이 앱에 들어온 뒤

1. **2-1** 로 그 사람의 uuid 를 받아
2. `0002_legacy.sql` §1 의 그 줄만 채우고
3. **파일 전체를** 다시 붙여넣어 **Run**

이미 들어간 전보함은 손대지 않고, 건너뛰었던 것만 들어갑니다. 이 순서를 일회용
Postgres 에서 실제로 밟아 확인했습니다 — 두 번에 나눠 부은 결과가 한 번에 부은
것과 같습니다.

### 4. 확인하고 치운다

1. 위쪽 전보함 이름을 눌러 **`견본 전보함 1` 와 `견본 전보함 2` 두 개**가 목록에 있는지

3. **타전실** — `견본 전보함 1` 는 이번 권이 VOL.4 이고 보낸 전보 한 통이 남아 있는지
4. 참여자 줄에 `견본 전보함 1` 는 세 명, `견본 전보함 2` 는 두 명인지

> **참여자 줄의 이름이 옛 앱과 달라도 정상입니다.** 서가에 꽂힌 책 속 이름은
> 제본 시점 스냅샷이라 `안` · `보` · `에피` 그대로입니다. 지금 이름이
> 신경 쓰이면 앱의 설정에서 바꾸면 되고, 바꿔도 옛 책은 변하지 않습니다.

**보·에피 화면에서**: 새로고침하면 전보함이 저절로 보입니다. 초대 코드를
넣을 일이 없습니다.

건너뛴 전보함이 있다면 그것만 아직 안 보입니다. **3-1** 이 남았습니다.

**두 전보함이 다 들어간 뒤에**: `public/migrate.html` 을 지웁니다. 옛 파이어베이스에서 데이터를

## 옮기면서 정한 것

옛 앱과 새 앱의 어휘가 달라 그대로 옮길 수 없는 자리들이다. 근거는 전부
`neon/migration/build.mjs` 의 주석에 같이 적었고, 값을 바꾸려면 그 스크립트를
고쳐 다시 뽑는다.

| 자리 | 어떻게 했나 |
|---|---|
| 초대 코드 | 옛 `coupleCode` 를 그대로 쓴다. 네 개 모두 새 형식(혼동 문자 I O 0 1 제외)에 맞는다 |
| 옮길 전보함 | `build.mjs` 의 `BOXES` 에 roomId 로 적는다. 이름은 바뀔 수 있고 roomId 는 안 바뀐다 |
| `견본 전보함 2` 의 소유자 | 옛 `ownerUid` 가 빈 문자열이라 안 를 놓았다 |
| 권 번호의 구멍 | 메꾸지 않는다 (`견본 전보함 2` 는 VOL.3 부터 시작한다) |
| 봉인 | 기본값 그대로 `true` (D1) |
| 타자기 | 옛 여섯 색 → 네 대. violet·rose→설탕, blue→강철, green·teal→이끼, ochre→참나무. 개인 설정이라 앱에서 바꿀 수 있다 (D9) |
| 용지색 | 원본 그대로. 공개 정보이고 발신인을 가리키는 값이다 |
| 사진 표지 8권 | 색 표지 `sage` 로 떨어뜨렸다. 어느 권이었는지는 `0002_legacy.sql` 머리말에 목록으로 남겼다 |
| 권의 기간 | `close_volume()` 과 같게 첫 전보·마지막 전보의 시각. 원본의 기간 문자열과 날짜가 10권 모두 일치하는 것을 확인했다 |
| 페이지 시각 | 옛 기록에 `07.21 15:16` 처럼 연도가 없다. 연도는 그 권의 기간에서, 시간대는 KST 로 읽었다 |
| 권 제목 | 옛 제목이 `VOL.n` 라벨과 같으면 비운다 — 서가가 `VOL.n` 을 따로 그려서 두 번 찍힌다 |
| `read_together` | `true`. 옛 앱에는 '함께 읽기' 단계가 없었다(D2 는 새 결정). `false` 로 두면 옛 책 열 권마다 "함께 읽기를 건너뛰고 제본했습니다" 가 찍힌다 |
| `견본 전보함 2` VOL.3~7 의 `a` / `b` | `a`=안, `b`=에피. VOL.7 에서 `a` 의 전보가 07.21 13:20 에 끊기고 같은 날 저녁부터 안 의 실제 uid 로 이어진다. VOL.7 의 `a` 행에만 남아 있던 이름 `?` · 용지 `ivory` 도 안/powder 로 통일했다 — 그대로 두면 그 권에서만 한 사람이 두 색으로 보인다 |

## 개발자용 부록

```bash
node neon/migration/build.mjs   # legacy-export.json → 0002_legacy.sql
neon/migration/dryrun.sh        # 일회용 Postgres 에 부어 보고 세어 본다
```

```bash
SKIP=보 neon/migration/dryrun.sh      # 그 사람만 빼고 부어 본다
NOPROFILES=1 neon/migration/dryrun.sh    # 프로필을 하나도 미리 만들지 않는다
```

`NOPROFILES` 는 계정만 만들고 앱에는 아직 못 들어온 상태를 재현한다. 이관 SQL 이
스스로 프로필을 세우고 끝까지 가야 한다. 둘을 함께 줄 수도 있다.

`SKIP` 을 주면 그 사람 줄을 `null` 로 남긴 판을 먼저 붓고, 이어서 전부 채운 판을
붓는다 — 실제 절차(§3 → §3-1)를 그대로 밟아 본다. 두 번에 나눠 부은 결과가 한 번에
부은 것과 같아야 한다.

`dryrun.sh` 는 §1 의 빈칸을 **세어 보고** 그만큼 가짜 uuid 로 채워 돌린다 —
`BOXES` 를 바꿔 사람 수가 달라져도 손댈 곳이 없다. 스키마(`0001_init.sql`)를
올리고, 프로필 넷을 만들고, 이관 SQL 을 **두 번** 부은 뒤 전보함별·권별로 세어
보여 준다. 마지막 표의 세 숫자(쪽수가 어긋난 권 · 한 권 두 색인 발신인 · 빈 권)는
전부 0 이어야 한다.
